This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A personal Telegram chatbot that will search the owner's Notion database of novels. The owner is a coding beginner, so explain steps simply, keep short comments in code, and write user-facing docs (README.md) in English.

The roadmap is the owner's plan document `Kế hoạch chi tiết Chatbot Telegram tìm truyện (Notion + Gemini).docx` (phases 0-5; finish one phase's "done when" check before the next). Phases 0-2 are done and verified live (sample questions give 0 / 2 / 1 / 7 stories). **Phase 3** (per-`chat_id` memory, tag synonyms, error handling and logging) is implemented; the owner still has to set the API spending limit and test on Telegram. **Phase 4** (add/update stories) is in progress: the data layer (`services/notion_write.py`, plus `find_books` / `find_duplicates` in `services/notion_search.py`) is done and tested only against a fake Notion. `/add` (`flows/add_flow.py`) and `/edit` (`flows/edit_flow.py`) are built and tested offline only; the owner now has to enable the integration's write capabilities and does a real test (4.6-4.7). See "Notion write" below. The search now picks randomly, defaults to unread books and supports "xem thêm" paging (see "Gemini" and "Notion search" below); the owner's main purpose for the bot is finding a NEW book to read.

- LLM provider is the **Gemini API**, not Claude/Anthropic. Do not install `anthropic`; the SDK is `google-genai`. Model comes from `GEMINI_MODEL` in `.env`, default `gemini-3.6-flash` (`gemini-2.5-flash` is deprecated; check the Google model list before changing).
- The Notion integration is **read-only** until Phase 4; no delete feature ever (use Reading Status = Drop instead).
- New secrets go in `.env.example` as empty keys (e.g. `GEMINI_API_KEY=`).

## Architecture

## Layout

```
bot.py            entry point (`python bot.py`): config check, error messages, handler wiring
logtools/         everything about logging: paths.py (the ONLY place with log file paths), context.py (req_id, user-id masking),
                  redact.py (hides secrets), setup.py (setup_logging), summary.py (`python -m logtools.summary`)
services/         no Telegram code: notion_search.py (read), notion_write.py (the ONLY writer), gemini_agent.py, render.py (writes the story list)
flows/            Telegram conversations: __init__.py (joins /add + /edit), add_flow.py, edit_flow.py
tests/            test scripts, run with `python -m tests.<name>`
logs/             bot.log (errors) and writes.log (every Notion write); git-ignored, created automatically
```

Import rule: `bot.py` → `flows`, `services` and `logtools`; `flows` → `services` and `logtools`; `services` never imports `flows` or `bot` (it may import `logtools.paths`); `logtools` imports nothing from the project. Imports are absolute (`from services import notion_search`). `load_dotenv()` finds the root `.env` from inside `services/` by walking up.

Flow: Telegram message → `bot.py` → `services/gemini_agent.answer_question` → ONE Gemini request: Gemini only picks the search filters by asking for the `find_stories` tool → our code runs `find_stories` → `services/notion_search.search_stories` queries Notion → `services/render.py` writes the Vietnamese list. The result is NOT sent back to Gemini (this removed the second request: about 80% fewer tokens and ~2 s instead of ~5 s per question). Gemini never touches Notion directly and never sees Notion data.

### Bot (`bot.py`)

Built on `python-telegram-bot` (v22, async, long polling via `app.run_polling()`).

- **Config** is read from `.env` with `python-dotenv`. The script exits with a message at startup if `BOT_TOKEN`, `TELEGRAM_USER_ID` (must be numeric), `NOTION_TOKEN`, `NOTION_DATA_SOURCE_ID` or `GEMINI_API_KEY` is missing. `NOTION_DATA_SOURCE_ID` holds ALL the lists, comma-separated, in order (the first is "list 1"; search + duplicate warning). Optional `NOTION_ADD_DATA_SOURCE_ID` = the ONE list where `/add` puts new stories (empty = the first; the owner uses list 3). There is no `NOTION_EXTRA_DATA_SOURCE_IDS` any more: `bot.py` logs a WARNING if it (or the short-lived `NOTION_EDIT_DATA_SOURCE_ID`) is still in `.env`, and logs which lists are in use at startup.
- **Single-user access control** is done with a `filters.User(user_id=ALLOWED_USER_ID)` filter attached to every handler (`only_me`). Messages from anyone else match no handler and are silently ignored. Any new handler must include this filter, or it will respond to strangers.
- Free text (`only_me & filters.TEXT & ~filters.COMMAND`) goes to `answer_question(chat_id, text)` inside `asyncio.to_thread`, because the Gemini and Notion SDK calls used are synchronous.
- **Logging** lives only in the `logtools/` package. `bot.main()` calls `logtools.setup_logging()` as its first line (importing `bot` does NOT switch logging on, so tests can import it safely; `setup_logging(log_dir=...)` takes a temporary folder for tests and returns the log file path). Result: terminal + rotating `logs/bot.log` (1 MB, 3 backups), level from `LOG_LEVEL` in `.env` (default INFO), line format `time LEVEL [req_id] message`. `handle_question` gives each question a 5-character `req_id` (a `contextvars` variable, so it also reaches the worker thread and every library log line) and logs, in order: `Incoming` (user id masked to 4 digits + `***`, length, first 50 characters only), `Gemini model_request=N time=… status=… prompt=… output=…` (one line per Gemini request, from the httpx2 hooks in `gemini_agent.py`), `Gemini function call` (name + filters), `Notion query: results=… time=…`, `usage:`, `Reply sent: chars=…` (only when Telegram accepted the reply), `Done: status=ok|error total_time=…`. WARNINGs: a message from a user who is not allowed (`reject_stranger`, group 1 handler: logs only, never replies) and Notion returning 0 results. Errors use `logger.exception` with the source named (`error_source()`: Notion / Gemini / timeout / unexpected). **Secrets:** `logtools/redact.py` blanks the real values of `BOT_TOKEN`, `NOTION_TOKEN`, `GEMINI_API_KEY` and token-shaped strings in every line, tracebacks included. Never log story lists (counts only). The `httpx`, `httpcore`, `httpx2` and `httpcore2` loggers stay at WARNING whatever `LOG_LEVEL` is, because their INFO logs print every request URL (Telegram URLs contain the bot token; Gemini's library uses `httpx2`). Do not log the text of a Telegram `NetworkError`; `on_error` logs only its type. **`/add` and `/edit` logging** (`flows/flowlog.py`): each conversation gets ONE log id (`flowlog.begin`, stored in `user_data[key]["log_id"]`), and every registered handler is wrapped with `@flowlog.tracked(DATA_KEY)` which puts that id back with `logtools.set_req_id` (each button press runs in its own task, so without it the lines would show `[-]`). Lines are `/add <step>: <result>` (e.g. `/add link: ok host=example.com`, `/add duplicate check: found=1 in_lists=[2]`, `/add confirm: writing to Notion (list 3)`, `/add done: added name=… list=3 id=L3-90 page_id=… total_time=…`, `/add cancelled at step '…'`), `Notion write: add list=3 code=L3-90 page_id=…` comes from `notion_write._log_write` under the same id, and a refused old Confirm button is a WARNING. Never log typed text: only lengths, counts and the website of a link (`flowlog.host_of`); the story name appears only in the final `done`/`picked` lines (cut to 50 chars) because writes.log already holds it. `logs/writes.log` uses the same date-time style as bot.log (`2026-11-10 10:51:10`). `tests/test_add_flow.py` and `tests/test_edit_flow.py` check these lines. `python -m tests.test_logging` (75 checks) and `python -m tests.demo_log` cover this. `logs/writes.log` takes its path from `logtools.paths.WRITES_LOG` too (`notion_write.WRITE_LOG_PATH`).
- google-genai uses the `httpx2` library, whose errors do NOT inherit from `httpx`'s. `friendly_error()` therefore checks both (`NETWORK_ERRORS` / `TIMEOUT_ERRORS`). It names the real cause: Notion `rate_limited`/429, 5xx and permission/sharing errors get different messages (never blame the token for a rate limit); Gemini 429/401/403/404/5xx; timeouts; network. In `/add` and `/edit`, only `restricted_resource`/`unauthorized` send the owner to the "Insert/Update content" permission; any other Notion error uses `friendly_error` plus "check Notion before retrying". `on_error` is the app-wide error handler (one short log line instead of a traceback).

### Gemini (`services/gemini_agent.py`)

**One request per question.** `answer_question` calls `client.models.generate_content` once, with `tools=[find_stories]` and `automatic_function_calling` DISABLED, so the SDK returns the function call instead of running it and feeding the result back. Our code then runs `find_stories` (through `_run_search`, which validates and fixes Gemini's arguments: wrong types or an unknown function give a polite "chưa hiểu" message, never a crash) and `render.render_result` writes the list: header with total + conditions + "gợi ý ngẫu nhiên", numbered stories (name - author - chapters, tags, link), and the "xem thêm" footer with `remaining`. If Gemini answers with text instead of a function call (off-topic, or asking which tag), that text is returned as is. A Notion error now propagates to `bot.py`, so the user gets the friendly message from `friendly_error` (before, the SDK hid it inside the tool and Gemini paraphrased it). Do not give Gemini any other tool, and do not turn automatic function calling back on (the SDK would run the tool and make the second, expensive request).

**Memory** is `_history[chat_id]`, a list of exchanges (in memory, lost on restart), trimmed to the last `MAX_EXCHANGES` (5). An exchange is stored very small: the user's question, Gemini's model message kept exactly as received (the function call, with its thought signature, which Gemini 3 models need back), a function response holding only numbers (`total/skip/shown/remaining`) and one note line from `render.history_note` ("Đã hiển thị truyện 1-10 trong 25 truyện (…)"). Story names are NOT remembered, so a follow-up like "truyện số 3 là gì?" is not supported; follow-ups that change the conditions ("chỉ lấy truyện đã hoàn thôi") and "xem thêm" are. A failed question is not remembered. One lock serializes calls. `SYSTEM_PROMPT` and the `find_stories.__doc__` built in `_config()` (live tag list from Notion, names only) are short on purpose because they are sent with every question: edit that docstring (not the signature) to change what Gemini is told, and keep them free of anything that changes between questions (the provider can then cache the repeated start). `MAX_OUTPUT_TOKENS` (512) caps every reply.

**Token and time numbers.** `response.usage_metadata` is not used; `_count_usage` is an httpx2 response hook (with `_mark_request_start` as the request hook for timing), attached through `HttpOptions(client_args={"event_hooks": ...})` in `_http_options()`. It logs one `Gemini model_request=N time=… status=… prompt=… output=…` line per request and adds up the tokens into `_usage`, which `answer_question` resets before and logs after each question as `usage: model=… prompt=… output=… function_calls=… model_requests=… total=…` (`thinking=`/`cached=` only when non-zero, `n/a` for numbers Gemini did not send). `function_calls` = how many times Gemini called `find_stories`; `model_requests` = how many requests we sent to Gemini (now 1 per question; the free tier allows 15/min). The library's own `AFC remote call N` lines are no longer logged (AFC is off). `python -m tests.test_usage` checks the counting against a fake Gemini server, and `python -m tests.test_one_request` (41 checks, fake Gemini + fake Notion) checks the one-request flow, the memory contents, odd replies, the thought signature and the memory limit. The Gemini client has a 60 s timeout (`GEMINI_TIMEOUT_MS`): the library's default is no timeout, and one hung request would hold `_lock` forever and freeze every later question.

**Finding new books (random pick, default unread, "xem thêm").** Each NEW search gets a random seed and `search_stories` shuffles all matches with it, so repeated questions give different suggestions instead of always Notion's first 10. `_search_state[chat_id]` (in memory, lost on restart) stores that search's filters, seed and how many were shown; when Gemini calls `find_stories(next_page=True)` the stored filters and seed are reused (Gemini's repeated filters are ignored) and the next 10 come back, so "xem thêm" never repeats within a search. `_current_chat_id` is set in `answer_question` under the lock so the tool knows which chat is asking. `SYSTEM_PROMPT` tells Gemini to default to `reading_status="Not started"` for suggestion requests (the rendered header then says "chưa đọc"), but NOT for author/title lookups or when the user mentions reading progress. Calling it with `next_page=True` when there is no stored search (e.g. right after a restart) returns an error whose text is shown to the user ("Hãy hỏi lại câu tìm truyện"), instead of silently running a new search. The owner declined a "never repeat across different questions" memory: a new question may show books suggested earlier. `python -m tests.test_paging` checks this offline (30 checks).

### Notion search (`services/notion_search.py`)

`search_stories(tags, reading_status, status, max_chapters, author)` is the only place that talks to Notion; it is read-only and returns `{"total", "skip", "shown", "remaining", "stories"}` with at most 10 stories (it pages through all matches to count the total and to shuffle them; `seed=None` keeps Notion's order, a seed gives a repeatable shuffle, `skip` selects the batch). `notion-client` 3.x queries via `data_sources.query` with `NOTION_DATA_SOURCE_ID` (not the database ID). Table "List truyện 1" gotchas:

- **Several lists.** Lists 2 and 3 have the same columns as list 1 and the same connection. The settings are read once in `services/notion_search.py` into `DATA_SOURCE_IDS` and `ADD_SOURCE_ID` and used through `all_sources()` (every list, in `.env` order; the /add list is appended if missing, so a new story can always be found and edited), `main_source_id()` (the first list, the default for functions not told a list), `add_source_id()` and `list_number()`. `search_stories` queries each list, joins the matches (first list first), counts a story with the same link once, then shuffles/pages as one table, so "xem thêm" works across all lists. Every list has its OWN tag options (list 3 has `Cải trang`, lists 1-2 do not): `get_valid_tags(source_id)` is per list, `get_all_tags()` is the union (shown to Gemini and used to reject typos), and `build_filter(..., source_id, skip_missing_tags=True)` raises `NoMatchInThisList` so a list without the tag is skipped instead of queried. If one list fails (e.g. not shared with the integration) the error propagates, so the user never gets a silent partial answer. `find_duplicates` checks all lists (each result has `"list"`). **`/edit` works in any list of `all_sources()`:** `find_books` searches each of them (each book has `source_id`, `list` and its ID `code`, shown on the button), and `notion_write._page_source(page)` refuses any page whose parent is not one of our lists (a page of any other table in Notion is never touched) and returns the list the page is in, so the story's tags are checked and written with THAT list's option ids (`build_column_update(column, value, source_id)`; `update_story` rejects bad non-tag input before any Notion call, tags need the page first). `id_label(page)` (in `notion_search`) turns the `ID` column (Notion's automatic ID, or plain text in list 1) into `L3-91`. Known edge: a tag whose synonym exists in a list but the tag itself does not is skipped for that list. Tests that use a fake Notion pin `notion_search.DATA_SOURCE_IDS = notion_search.DATA_SOURCE_IDS[:1]` and `ADD_SOURCE_ID = None` so they do not depend on `.env`.

- The column is named `"Reading Status "` **with a trailing space**; the tag `" Cổ Đại"` has a leading space. Input is matched case-insensitively against real option names.
- `Status` (Full / In progress / Drop) is the story's own completion state ("đã hoàn" = Full); `Reading Status` (Not started / In progress / Done / Beginning + End / Drop) is the owner's reading progress ("chưa đọc" = Not started).
- `Trùng sinh` and `Trọng sinh` are near-duplicate tags; `TAG_SYNONYMS` in `services/notion_search.py` makes a search for either match both (OR inside the group, still AND with other tags; add further pairs there). Synonyms are matched against Notion's real tag names; one that was renamed or deleted is skipped with a warning in the log instead of breaking the search. `_client()` is cached (one Notion client reused), and the pagination loop also stops if Notion says `has_more` but sends no `next_cursor`.
- `max_chapters` is inclusive; multiple tags are AND-ed (owner chose strict AND; Notion's own UI "Contains" with several tags is OR, so compare by hand with one filter row per tag).
- Only 1 of ~199 stories has the `HE` tag; the owner chose to keep `HE` a strict filter and tag their stories in Notion rather than loosen it in code.
- 3 stories have no chapter count and never match a `max_chapters` search.

### Notion write (`services/notion_write.py`)

The only file that writes to Notion. Rules that must not be weakened:

- **Gemini never writes.** Writing happens only through the bot's guided `/add` and `/edit` conversations (the bot asks one column at a time; no free-text parsing by an LLM). Only a confirm button press from `ALLOWED_USER_ID` calls `add_story` / `update_story`. Do not give Gemini any write tool: the SDK runs any tool it is given immediately, so a prompt rule is not a safeguard.
- `/add` (`flows/add_flow.py`) and `/edit` (`flows/edit_flow.py`) are guided conversations, joined into ONE `ConversationHandler` by `flows/__init__.py` and registered in `bot.py` **before** the free-text Gemini handler. One handler (not two) so the bot is always in exactly one step of one flow: with two handlers, typing `/add` during `/edit` left both open and the next answer went to the wrong one. Their state numbers must not clash (`/add` uses 0-7, `/edit` 100-106), and each `start` clears the other flow's `user_data`. `/cancel` picks the right message by checking which flow's data exists. Every button step also has a stray-text handler that says "use the buttons", otherwise typed text would fall through to Gemini.
- **Where `/add` writes:** `add_story` creates the row in `notion_search.add_source_id()` (not always list 1). Every list has its OWN tag options, so tags are checked and written by option id of THAT list: `_tag_ids(source_id)` / `_tags_property(tags, source_id)` (None = list 1, used by `/edit`), and the `/add` tag buttons come from `get_valid_tags(add_source_id())`. The `/add` first message and the success message name the list ("List 3") and the automatic ID Notion gave the new row (`L3-90`, read from the `ID` unique_id property; `None` if the list has none). Lists 2 and 3 have an automatic `ID` column (prefix `L2`/`L3`); list 1's `ID` is a plain text column filled by hand (L1-1...L1-200), so for such a list `add_story` counts the next one itself (`_next_text_id`: highest existing number + 1 with the same prefix, e.g. `L1-201`; it sends nothing when the ID is Notion's automatic type, when the list has no `ID` column, or when there is no earlier ID to copy the prefix from). Either way the owner never types an ID by hand. 
- `/add` steps: name → link → duplicate warning (add anyway / cancel) → author → chapters → tags (tap-to-toggle buttons) → status → summary with Confirm / Cancel. Answers are validated by calling `notion_write.build_column_update` / `parse_chapters`, so the rules live in one place.
- `/edit` steps: type part of a name or author (`find_books`, up to 10 buttons; typing again searches again) → the story's current values and a column list → new value (text, tag buttons, or a list of values; only note and date offer "clear") → "Trước/Sau" with Confirm / Keep old value → written as ONE column → "Sửa cột nào nữa?" until Done. A value equal to the current one is skipped. The confirm button carries a one-time code (`edit:confirm:<nonce>`) that is used up before the write, so an old or double-pressed button can never confirm or repeat a change. `/add` has the same one-time confirm code (`add:confirm:<nonce>`), so after restarting `/add` an old summary's button is refused.
- Tests: `python -m tests.test_add_flow` (48 checks), `python -m tests.test_edit_flow` (61, including `/add`+`/edit` switching) and `python -m tests.test_write` drive the real handlers with a fake Telegram connection and a fake Notion: no real writes. None of it has been tried against real Telegram or a real Notion write yet.
- No delete, archive or trash code, ever; to drop a story set Reading Status = Drop. Notion has no separate delete permission, so this is enforced here, and `tests/test_write.py` greps for it.
- `update_story(page_id, column, value)` changes ONE column per call, only keys in `EDITABLE_COLUMNS` (all columns including Date, by the owner's choice). Only `note` and `date` may be cleared; every other column must keep a value. Note is replaced, not appended. It refuses pages outside our lists (`NOTION_DATA_SOURCE_ID`) and pages in the trash. `get_story` reads current values for display; `parse_chapters` / `parse_date` (accepts dd/mm/yyyy) convert typed text.
- `add_story`: name, author, chapters (at least 1), tags and link are all **required** (a missing one is rejected, and all missing items are listed together). Defaults: Status = Full, Reading Status = Not started, Record Audio = Not started; `Note` and `Date` are never sent, so they stay empty. Unknown tags are rejected; tags are written by option id (the tag `" Cổ Đại"` has a leading space).
- Every write is appended to `logs/writes.log` (git-ignored) with before/after values.
- `python -m tests.test_write` checks all of this against a fake Notion client, with no real writes. Real writes need the integration's "Update content" and "Insert content" capabilities (step 4.6) and have not been tested.

## Code style

The owner wants others to be able to read the code: every module starts with a docstring that explains its job, every function has a short docstring (including the handlers nested inside `build_add_handler` / `build_edit_handler`), and tricky lines get a short `#` comment saying WHY. `.env.example` is grouped by topic (Telegram, Notion, Gemini, Logging) with a comment for every key; keep that when adding a key. Keep comments short and in English.

## Secrets

`.env` is git-ignored and must never be created or filled by Claude. The user copies `.env.example` to `.env` and enters their own values. Never ask them to paste real tokens or keys into chat.
